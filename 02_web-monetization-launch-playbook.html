The core principle

Start with the smallest architecture that solves your actual problem. Extra services add complexity even when their initial price is zero.

Start here

1. Can you host a website for free?

Yes. Many websites can be hosted for $0 in hosting charges by using a provider's free tier. A static site—one served as files rather than generated by a continuously running application—is usually the easiest and most predictable place to start.

The important distinction is that free hosting is not the same as a free, unlimited production system. Requests, compute time, storage, bandwidth, builds, database activity and account eligibility may all be limited. A domain name, email delivery, paid APIs or other services may also cost money.

Good candidates for free hosting

  • Portfolios and personal websites
  • Documentation and learning resources
  • Landing pages and small business websites
  • Browser-based calculators and utilities
  • Prototypes, demos and small applications
  • Low-traffic projects within published quotas

Requires additional planning

  • Payment processing and sensitive customer data
  • Large video, image or download libraries
  • Long-running jobs and heavy computation
  • High-volume email or notification delivery
  • Strict uptime, compliance or support requirements
  • Commercial use restricted by a provider's plan

Important distinction

A free tier is an allowance defined by a provider, not a guarantee that every project will remain free indefinitely. Always review current pricing, overage rules, acceptable-use policies and commercial restrictions before launching.

Make the right choice

2. Choose a hosting stack for your project

Do not start by signing up for every platform in this guide. Identify the features your project needs, then select the minimum number of services required to provide them.

A

Static website

For HTML, CSS, JavaScript, documentation, blogs built as static files and marketing pages. Files are delivered directly to visitors, so no application server or database is necessary.

Consider: Cloudflare Pages or GitHub Pages.

B

Website with a small API

For form processing, private API calls, input validation, simple integrations or request-based business logic. Run sensitive operations on a server instead of trusting browser JavaScript.

Consider: Static hosting + Cloudflare Workers.

C

Application with persistent data

For accounts, orders, structured records, submissions and data that must survive beyond a browser session. Choose a database based on query patterns, consistency, storage and backup needs.

Consider: Serverless API + Neon Postgres, or a suitable key-value store.

D

Full-stack framework application

For server-side rendering, framework-specific routing, image processing or server components. Verify that the selected platform supports the exact features your framework requires.

Consider: A framework-compatible platform with suitable free and paid plans.

Practical recommendation

For a guide page like this GetKit article, static hosting is enough. You do not need Workers, KV or Postgres simply to display text, navigation, links and a client-side checklist.

Understand the pieces

4. How a zero-cost web architecture works

A typical web application has three separate responsibilities: displaying the interface, executing trusted server-side logic and storing persistent information. Keeping these responsibilities separate helps you secure and maintain the application.

Visitor's browser

HTML · CSS · JavaScript

↓ HTTPS request

Static host / CDN

Serves pages and public assets

↓ When dynamic logic is needed

Serverless API

Authentication · Validation · Business logic

KV storage

Suitable for key-value data and cache-like use cases

Postgres database

Relational records, constraints and transactions

What each component does

  • Browser: Displays the interface and runs public client-side code. Anything delivered to the browser should be considered visible to users.
  • Static host/CDN: Delivers HTML, CSS, JavaScript, images and other assets, often from a nearby edge location.
  • Serverless function: Runs request-based logic without requiring you to administer a conventional always-on server.
  • KV store: Stores values associated with keys. It is useful for suitable lookup and configuration workloads, but not a direct replacement for every relational database.
  • Postgres: Stores structured data and supports relationships, constraints, transactions and SQL queries.

Security rule

The browser should never receive database passwords, private API keys or privileged tokens. Put secrets in server-side environment variables or the provider's secret-management system.

First deployment

5. Deploy a static website with Cloudflare Pages

A static site is the easiest place to start because it avoids database setup, server maintenance and backend security concerns. You can use a Git-based workflow or a supported direct-upload method, depending on your project and the platform's current options.

Step 1 — Prepare your files

A simple project might look like this:

my-website/
├── index.html
├── about.html
├── assets/
│   ├── css/
│   │   └── style.css
│   ├── js/
│   │   └── main.js
│   └── images/
└── README.md

Make sure your home page is named index.html when using a standard static-file setup. Use relative paths for assets when appropriate, and test internal links before publishing.

Step 2 — Test locally

Open the page in your browser and inspect it at desktop and mobile widths. If the project relies on JavaScript modules, fetch requests or routing behavior, use a local development server rather than assuming opening the file directly will reproduce production behavior.

Step 3 — Create a deployment

  1. Create or sign in to your Cloudflare account.
  2. Open the Pages area in the dashboard.
  3. Choose the currently supported deployment method for your project, such as connecting a Git repository.
  4. For plain HTML and CSS, configure the build settings according to the current Pages documentation. A build command may not be required for a simple static project.
  5. Deploy and open the generated URL.
  6. Check the published page, links, browser console and mobile layout.

Step 4 — Connect a custom domain if needed

A platform-provided subdomain may be sufficient for testing. A custom domain usually requires a separate domain registration or renewal fee. Follow the platform's DNS instructions carefully and allow time for DNS changes to propagate.

Before publishing

Do not upload private environment files, API keys, database exports or confidential documents into a public repository or static hosting directory. A file is not private merely because you do not link to it.

Official instructions: Cloudflare Pages documentation.

Add backend functionality

6. Use Cloudflare Workers for serverless APIs

A serverless function lets your website perform trusted operations on the server side. Typical examples include validating form submissions, calling an external API with a private credential, processing small requests or checking access permissions.

Example: a minimal Worker endpoint

The following example returns JSON for a simple health-check route. It is deliberately small: it demonstrates request handling, not a complete authenticated application. 

export default {
  async fetch(request) {
    const url = new URL(request.url);

    if (request.method === "GET" && url.pathname === "/health") {
      return Response.json({
        ok: true,
        service: "getkit-api"
      });
    }

    return Response.json(
      { error: "Not found" },
      { status: 404 }
    );
  }
};

This example uses the Workers module syntax. Save it in the format required by your chosen deployment workflow, configure the entry point and deploy according to the official documentation.

When adding a real endpoint

  • Allow only the HTTP methods your route needs.
  • Validate request bodies, content types and input lengths.
  • Return appropriate HTTP status codes.
  • Keep credentials in server-side secrets, never in frontend JavaScript.
  • Protect sensitive routes with authentication and authorization.
  • Use rate limiting or other abuse controls when exposed publicly.
  • Do not return raw stack traces, internal configuration or database errors to users.

Understand the free-tier trade-off

Workers Free has documented request and CPU limits. The published allowance has included 100,000 requests per day and 10 milliseconds of CPU time per invocation; confirm the current pricing and limits before relying on these numbers for a live application. External network waits and CPU execution are different parts of request behavior.

Official documentation: Cloudflare Workers · Pricing and usage.

Key-value storage

7. Cloudflare KV: what it is and when to use it

Cloudflare Workers KV is a key-value storage service designed for globally distributed reads. An application stores a value under a key and retrieves it later. It is useful for some configuration, lookup, cached content and other workloads that tolerate its consistency characteristics.

Good uses for KV

  • Public or non-sensitive configuration values.
  • Cached content that can be regenerated.
  • Simple key-based lookup data.
  • Small pieces of application state that fit KV's data model.

When KV is the wrong tool

Do not choose KV just because it sounds easy or is available on a free plan. Relational transactions, complex queries, uniqueness constraints and tightly consistent read-after-write workflows may require a different storage system.

Do not store passwords as plain values

Authentication data, sensitive personal information and authorization state require careful design. A key-value store does not automatically provide a secure user-management system. Use established authentication patterns and appropriate access controls.

A conceptual example

// Conceptual Workers KV example.
// Bind a KV namespace as SETTINGS in your Worker configuration.

export default {
  async fetch(request, env) {
    const value = await env.SETTINGS.get("site-message");

    return Response.json({
      message: value ?? "Welcome to GetKit"
    });
  }
};

This snippet assumes a KV namespace binding named SETTINGS has already been configured. The code alone does not create the namespace or configure permissions.

Official documentation: Cloudflare Workers KV.

Persistent application data

8. Neon Postgres: managed relational databases

A relational database becomes useful when your application needs persistent records, relationships, structured queries or transactions. Neon provides managed PostgreSQL with serverless-oriented features. The database is a separate component from the site that displays it.

When Postgres makes sense

  • User profiles and application records.
  • Orders, product metadata and structured content.
  • Relationships between users, projects and other entities.
  • Queries that need joins, indexes or transactions.
  • Data integrity enforced by database constraints.

Plan a simple schema first

For example, a basic notes application might use a table like this. This is schema illustration only; an actual application must also implement access control and server-side validation.

CREATE TABLE notes (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title TEXT NOT NULL,
  body TEXT NOT NULL DEFAULT '',
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX notes_created_at_idx
ON notes (created_at DESC);

Safe database integration principles

  1. Connect through a server-side function or backend designed for your runtime.
  2. Store the database connection string in a protected secret, not in browser code.
  3. Use parameterized queries instead of constructing SQL by concatenating user input.
  4. Give the application only the database privileges it needs.
  5. Validate and authorize every read or write operation.
  6. Review connection limits, pooling, compute suspension, storage and backup options.
  7. Test restore procedures for important production data.

Do not connect a static page directly to a private database

A browser is an untrusted environment. If a database password or privileged connection string appears in HTML or JavaScript delivered to visitors, assume it has been exposed. Use a backend boundary to control access.

Official documentation: Neon documentation · Neon pricing.

Protect your project

9. Security essentials for free-hosted websites

A free hosting plan does not remove the need for security. Many serious vulnerabilities come from application design, exposed secrets, overly broad permissions or missing validation rather than the hosting provider itself.

1. Protect secrets

Use environment variables or a provider's secret store for private API keys, database URLs and signing keys. Never commit secrets to Git. Rotate credentials if they are accidentally exposed.

2. Validate data on the server

Client-side checks improve usability but can be bypassed. Re-check input type, length, format and business rules on the server before processing or storing it.

3. Use parameterized database queries

Do not build SQL by inserting raw user input into a query string. Use the database driver's parameter-binding mechanism and grant only necessary database privileges.

4. Implement real authorization

Knowing a URL or record ID must not be enough to access private information. Verify the current user's permissions on every protected operation.

5. Control abuse

Public APIs and forms may be abused by automated clients. Consider rate limits, request-size limits, quotas, bot controls and appropriate anti-spam measures.

6. Plan backups and recovery

A deployment rollback is not the same as a database backup. Maintain recoverable copies of important data and verify that you can restore them.

7. Keep dependencies under control

Use maintained packages, remove unnecessary dependencies, review updates and monitor security advisories for the frameworks and libraries your project relies on.

A practical warning

Do not store payment card details yourself unless you have the expertise and compliance controls required. Prefer established payment providers and follow their integration guidance.

Know the trade-offs

10. Free-tier limits, hidden costs and upgrade signals

The goal is not to avoid every future expense at any cost. The goal is to understand what you are getting, operate within the plan and know when paying for reliability or capacity becomes sensible.

What can consume your allowance?

Resource Why it matters What to monitor
Requests Each page asset or API call may contribute to usage under the relevant service's rules. Request volume, repeated polling and bot traffic.
CPU / compute Expensive processing can exceed execution allowances. Function duration, query efficiency and CPU use.
Bandwidth / transfer Large assets and high traffic can increase transfer usage. Image sizes, video delivery and downloads.
Database storage Persistent data grows as records and indexes accumulate. Storage, index growth and unused records.
Database compute Queries, connections and active workloads consume resources. Query latency, connection usage and compute consumption.
Builds Frequent deployments can use build minutes or other allowances. Build frequency, failures and build duration.
External services Email, APIs, media and monitoring may have separate pricing. Vendor quotas, usage caps and renewal costs.
Domain A custom domain usually requires registration and renewal. Annual renewal price and DNS configuration.

How to estimate whether a free plan is enough

Do not estimate capacity using visitor counts alone. Visitors behave differently: one may load a single cached page, while another may trigger multiple API calls and database queries.

Illustrative workload calculation

Suppose a site receives 10,000 visits in a month. If each visit causes 8 requests to a particular service, that is approximately 80,000 requests for that service over the month. If each visit triggers 3 API calls, that is approximately 30,000 API calls. These are estimates, not provider billing predictions.

Real usage depends on caching, retries, prefetching, asset delivery, bot traffic, service-specific counting rules and actual visitor behavior.

When should you consider upgrading?

  • You repeatedly approach published limits during normal usage.
  • Your app needs more compute, storage or throughput.
  • You need a plan with commercial rights or additional contractual terms.
  • You need stronger support, observability, backups or operational controls.
  • The cost of an outage or exhausted quota is greater than the plan's price.
  • Your product's revenue or business model justifies predictable infrastructure spending.

Avoid surprise bills

Before deploying, determine whether exceeding an allowance causes a hard limit, temporary restriction, service degradation or billable usage. Enable usage alerts and spending controls wherever available, and review the dashboard after launch.

Fix common problems

11. Troubleshooting free-hosted websites

The website displays a 404 page after deployment

Check the published output directory, entry-point filename, route configuration and asset paths. A static deployment may not automatically support application-style routes. Review the platform's deployment logs and routing documentation.

CSS or images work locally but not online

Check file-name capitalization, relative paths, missing files and browser network errors. Some local environments tolerate path differences that fail on case-sensitive production systems. Confirm that each asset was included in the deployed output.

The API works locally but fails in production

Verify production environment variables, runtime compatibility, route paths, HTTP methods, authentication, CORS policy and external service availability. Inspect server-side logs without exposing secrets to the browser.

The database connection fails intermittently

Check connection limits, credentials, network access, compute availability, pooling configuration and provider status. Review query timeouts and database errors in protected server-side logs.

Requests fail after a traffic spike

Inspect usage dashboards and logs. Look for bots, retry loops, repeated polling, large uncached responses and expensive queries. Add caching where appropriate and enforce suitable limits on public endpoints.

The deployment succeeds but the app is slow

Measure before changing architecture. Inspect image size, JavaScript bundles, network requests, cache headers, database queries and third-party scripts. A geographically distant database or a cold-starting service may contribute to latency.

A third-party API rejects requests

Check the API key, account permissions, quota, endpoint URL, request schema and provider status. If the key is private, call the service from a backend function rather than embedding the key in public JavaScript.

Common questions

13. Frequently asked questions

Can I host a website for free forever?

You may be able to keep a project on a free plan while the plan exists and your usage remains eligible. However, providers can change their features, quotas and terms. Keep backups and understand how you would migrate.

Can I use free hosting for a business website?

It depends on the provider and the specific plan. Some plans restrict commercial use. Check the applicable terms before using a free plan for a monetized or business-critical project.

Do I need a database for a normal website?

No. A static website can display pages without a database. A database becomes useful when you need to store and query persistent information such as user profiles, submissions, orders or editable content.

Can a free host handle 100,000 visitors?

Possibly for some workloads, but visitor count alone is not enough to estimate capacity. File sizes, cache hit rate, API calls, database queries, bot traffic and plan rules all affect resource consumption.

Is Cloudflare Pages the same as Cloudflare Workers?

No. Pages is commonly used to publish websites and static assets. Workers runs code in response to requests. They can be used together, but the limits and capabilities of the feature you use still matter.

Is KV a replacement for Postgres?

Not generally. KV is a key-value store suited to particular lookup and distributed-read patterns. Postgres provides relational tables, SQL queries, transactions and constraints. Choose based on the data model and consistency requirements.

Does a free hosting plan include a custom domain?

Some providers offer a free platform subdomain and allow you to connect a domain you already own. Domain registration and renewal usually cost extra.

What is the safest way to avoid unexpected charges?

Read the pricing page, identify billable overages, configure usage alerts or limits where available, protect public endpoints and monitor consumption after launch.

Should I use a VPS instead?

A VPS can provide more control and support workloads that do not fit a serverless model. However, you become responsible for operating-system updates, server security, monitoring, backups and maintenance. Compare the total workload, not only the advertised price.
