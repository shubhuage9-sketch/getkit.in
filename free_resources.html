Free resources for builders

Six practical guides on hosting, launching, styling, backends, deployment and email. Each card below gives the key takeaways and the mistakes to avoid. Open the full guide when you need the steps.

8 rules that appear in every guide

  1. Free is not unlimited. Check quotas and commercial-use terms before you launch.
  2. Never put secrets in frontend code. Keys and database URLs belong in server-side environment variables.
  3. Start simple. Static hosting first. Add a backend or database only when a feature needs it.
  4. Validate on the server. Browser checks can be bypassed.
  5. CORS is not security. Add real authentication and authorization.
  6. Test the live site, not just your local copy or a green build.
  7. Keep a rollback path: a Git copy of your code, backups of your data, a known-good deployment.
  8. Don't paste placeholders. Use the exact values your provider gives you for DNS, keys and URLs.

The Zero-Dollar Web Hosting Guide

+Hosting · Cloudflare, GitHub Pages, Neon

Launch a site on free tiers and know when you'd need to pay.

Key takeaways

  • Pick the smallest stack: static site (Cloudflare Pages or GitHub Pages) → add Workers for server logic → add a database (Neon Postgres or Turso) only for saved data.
  • KV is for lookups and config. Use Postgres for relational data and transactions.
  • Deploy flow: organize files with index.html → push to GitHub → connect the repo to your host → test the live URL.
  • Rough bandwidth check: monthly views × page size. 10,000 views × 1 MB ≈ 10 GB.

Watch out

  • Vercel Hobby is for personal, non-commercial use.
  • Workers Free has been published at 100,000 requests/day and 10 ms CPU per call. Recheck before relying on it.
  • A custom domain still costs money. Plan upgrades when you keep hitting limits.
  • Never connect a browser directly to a private database.

Web Monetization & Launch Playbook

+Monetization · Offers, payments, trust pages, launch checklist

Turn a working site into something people can pay for, and launch it safely.

Key takeaways

  • Start with one clear offer for one clear audience. Add more products only after the first one sells.
  • Pick a single monetization path to begin with: digital products, templates, services, affiliate links or ads.
  • Publish the trust pages before you take money: about, contact, privacy policy, terms and refund policy.
  • Use a hosted checkout from a payment provider instead of building your own payment form.
  • Track a few numbers only: visitors, sign-ups or clicks, sales, and revenue per visitor.

Watch out

  • Check that your hosting plan allows commercial use before you start charging.
  • Never mark an order paid because of a browser redirect. Confirm it from the provider's webhook.
  • Disclose affiliate links and sponsored content, and don't promise income or results.
  • Do a real test purchase and download on the live site before announcing the launch.

Responsive Design & Tailwind CSS Architecture

+Frontend · Tailwind v3 and v4, accessibility, performance

Build consistent, accessible, fast interfaces.

Key takeaways

  • Utility-first CSS gives you a fixed vocabulary for spacing, type and color. Turn repeated patterns into components.
  • Use semantic design tokens like --color-surface, not names like --dark-gray-2.
  • Build mobile first. Add breakpoints where the layout breaks, and give images width and height to avoid layout shift.
  • Aim for good Core Web Vitals: LCP (loading), INP (interaction), CLS (stability).

v3 vs v4 setup

v3: @tailwind base;  + tailwind.config.js
v4: @import "tailwindcss";  + @theme { ... }
Check yours: npm ls tailwindcss

Watch out

  • Don't build class names dynamically (bg-${color}-600). The build can't detect them. Map to full class strings.
  • The Tailwind CDN is for demos. Use a compiled, version-pinned build in production.
  • Don't mix v3 and v4 instructions.
  • Use native buttons and links, visible labels and focus styles. Don't rely on color alone.

04

Full-Stack API & Database Engineering

+Backend · REST, PostgreSQL, Drizzle, Hono, security

Design secure APIs and reliable data models.

Key takeaways

  • Start with REST. Choose GraphQL or gRPC only for a clear reason (complex clients, typed internal services).
  • Let the database enforce rules: primary and foreign keys, unique and check constraints, transactions.
  • Store money as integer minor units (paise or cents), never floats.
  • Use parameterized queries. Return only the fields a client should see.
  • Measure before indexing: EXPLAIN (ANALYZE, BUFFERS).

Watch out

  • CORS is not authentication. Check identity and ownership on every protected route.
  • Never mark an order paid because of a browser redirect. Verify the provider's webhook and make it idempotent.
  • Never expose private file keys. Give buyers short-lived signed download URLs.
  • Budget connections: 20 per pool × 10 replicas can mean 200 connections.
  • Rate-limit login, reset and write routes with an atomic counter, not a plain KV read-then-write.

05

Git, GitHub & CI/CD Deployment Workflow

+Deployment · Pull requests, Cloudflare Pages, Vercel, headers

Ship changes safely and recover fast when something breaks.

Key takeaways

  • Flow: short-lived feature/... branch → pull request with checks → merge to main → host auto-deploys.
  • Enforce the rules on GitHub (branch protection or rulesets). Local hooks are only a convenience.
  • Stage specific files and read git diff --staged before committing.
git switch -c feature/update-guide
git add path/to/file.html
git diff --staged
git commit -m "docs: improve guide"
git push -u origin feature/update-guide

Watch out

  • On a shared branch use git revert, not force-push.
  • A host rollback and a Git revert are different. A rollback can't undo database changes.
  • Long immutable caching is only for content-hashed assets. Revalidate HTML.
  • Put _headers inside the deployed output folder. Test CSP and HSTS before enabling them.
  • Never commit keys or tokens.

06

Custom Domain DNS, Email Routing & SMTP

+Domain & email · MX, SPF, DKIM, DMARC

Get a branded address like support@yourdomain and keep it out of spam.

Key takeaways

  • DNS decides where mail is delivered and who may send it.
  • Cloudflare Email Routing only forwards incoming mail. It is not a mailbox and not an SMTP sender. Choose a separate way to send.
  • SPF lists allowed senders. DKIM signs messages with a key your provider gives you. DMARC sets what happens when checks fail.
  • Roll out DMARC in stages: p=none → p=quarantine → p=reject.
dig example.com MX +short
dig example.com TXT +short
dig _dmarc.example.com TXT +short

Watch out

  • Keep one SPF record per hostname and stay within 10 DNS lookups.
  • Don't change MX records without a plan. You can interrupt existing mail.
  • Don't invent DKIM selectors or keys. Use the exact record from your provider.
  • Never put SMTP passwords or private keys in frontend code or a public repo.
  • Test with real emails and check the SPF, DKIM and DMARC results in the headers.
