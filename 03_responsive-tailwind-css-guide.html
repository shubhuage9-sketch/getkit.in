01 · Foundations

1. Architecture overview: from visual design to a maintainable system

A design system is more than a collection of colors and reusable cards. It is a shared set of design decisions, interface patterns, accessibility rules and implementation conventions that help a website remain consistent as it grows.

Design foundationsColor · Type · Spacing · Radius · Elevation
↓
Layout primitivesContainer · Grid · Flexbox · Responsive rules
↓
Reusable componentsButtons · Cards · Forms · Navigation · Dialogs
↓
Page compositionsLanding pages · Dashboards · Documentation
↓
Quality and deliveryAccessibility · Tests · Performance · Monitoring

Consistency

Shared tokens and component patterns reduce small visual differences across pages and features.

Maintainability

A centralized design decision can be updated without manually editing every page.

Accessibility

Reusable patterns make keyboard behavior, labels, focus styles and contrast easier to audit.

Performance

Predictable styling and production builds help keep CSS manageable and avoid unnecessary client-side work.

Core principle Do not build a design system merely to create more abstractions. Create shared components when patterns genuinely repeat, and keep one-off layouts simple until reuse is justified.

02 · Styling strategy

2. Utility-first CSS: why it works

Utility-first CSS composes small classes to express layout, spacing, typography, color and state directly in markup. Instead of inventing a new class for every visual combination, developers reuse a controlled vocabulary of styling utilities.

Traditional CSS compared with utility-first styling

Traditional CSS
<div class="product-card">
  <h2 class="product-card__title">Starter Bundle</h2>
  <p class="product-card__description">
    A practical collection of digital resources.
  </p>
</div>

/* CSS */
.product-card {
  padding: 1.5rem;
  border: 1px solid #29364b;
  border-radius: 1rem;
}
.product-card__title {
  margin: 0 0 .75rem;
  font-size: 1.25rem;
  font-weight: 800;
}
Utility-first example
<div class="rounded-2xl border border-slate-700 p-6">
  <h2 class="mb-3 text-xl font-extrabold">
    Starter Bundle
  </h2>
  <p class="text-slate-400 leading-7">
    A practical collection of digital resources.
  </p>
</div>

Advantages

  • Local visibility: The markup reveals most of the element's styling without searching through multiple files.
  • Consistent spacing: A spacing scale reduces arbitrary values and accidental inconsistency.
  • Fast iteration: Responsive and interaction variants can be composed at the point of use.
  • Production extraction: A properly configured build can emit only the utilities used by the project.

Trade-offs

  • Long class attributes can become difficult to scan without formatting conventions.
  • Repeated patterns may need components to avoid copy-and-paste drift.
  • Runtime-generated class names can be missed by static source detection.
  • Arbitrary values can undermine consistency if used without design constraints.
Avoid dynamic class-name construction A build tool may not detect a class assembled from fragments such as bg-${color}-600. Prefer complete class strings or an explicit mapping from application state to known classes.
Reliable class mapping
const statusClasses = {
  success: "bg-emerald-500/10 text-emerald-300",
  warning: "bg-amber-500/10 text-amber-300",
  error: "bg-rose-500/10 text-rose-300"
};

function getStatusClass(status) {
  return statusClasses[status] ?? statusClasses.warning;
}

Use framework-specific syntax where required. In React, for example, the selected string would typically be passed through the element's className prop.

03 · Toolchain decisions

3. Tailwind CSS v3 and v4: understand the difference

Tailwind's configuration and build approach changed significantly between major versions. Do not mix installation commands or configuration assumptions from different versions. First identify the version used by the project, then follow its matching documentation.

Topic Tailwind v3 approach Tailwind v4 approach
Typical CSS entry @tailwind base; and related directives @import "tailwindcss";
Theme setup Frequently configured in tailwind.config.js CSS-first configuration through theme variables; JavaScript config support differs from v3
Source detection Configure content paths in the config file Automatic source detection with explicit controls when needed
Build integration Version-matched PostCSS or CLI setup Version-matched Vite plugin or PostCSS integration
Migration Existing project configuration Review compatibility, removed utilities and migration guidance

Example: a v3-style content configuration

tailwind.config.js — v3 example
/** @type {import('tailwindcss').Config} */
module.exports = {
  content: [
    "./index.html",
    "./src/**/*.{js,ts,jsx,tsx}"
  ],
  theme: {
    extend: {
      colors: {
        brand: {
          500: "#8b5cf6",
          600: "#7c3aed"
        }
      }
    }
  },
  plugins: []
};

Example: a v4-style CSS entry

src/input.css — v4 example
@import "tailwindcss";

@theme {
  --color-brand-500: #8b5cf6;
  --color-brand-600: #7c3aed;
  --font-family-sans: Inter, system-ui, sans-serif;
}
Before choosing a setup Check the installed package version in package.json or run npm ls tailwindcss. The snippets above are illustrative starting points, not complete installation instructions for every framework or build tool.

04 · Design foundations

4. Design tokens: build a consistent visual language

Design tokens are named values for recurring decisions: colors, spacing, typography, radii, borders and elevation. They allow the visual identity to evolve without scattering unexplained values throughout the application.

Example token layer using CSS custom properties

tokens.css
:root {
  --color-bg: #090d16;
  --color-surface: #101727;
  --color-text: #e8eef8;
  --color-muted: #a7b4c8;
  --color-border: #29364b;
  --color-brand: #67e8f9;

  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --space-3: 0.75rem;
  --space-4: 1rem;
  --space-6: 1.5rem;
  --space-8: 2rem;

  --radius-sm: 0.5rem;
  --radius-md: 0.75rem;
  --radius-lg: 1rem;

  --content-width: 1180px;
}

.card {
  padding: var(--space-6);
  border: 1px solid var(--color-border);
  border-radius: var(--radius-lg);
  background: var(--color-surface);
}

Token categories worth standardizing

Color

Background, surface, text, muted text, borders, brand, success, warning and error.

Spacing

A deliberate scale for gaps, padding, section rhythm and layout density.

Typography

Font families, sizes, weights, line heights and heading hierarchy.

Shape and depth

Border radii, border widths, shadows and overlay levels.

Use semantic names such as --color-surface rather than names that encode one current appearance, such as --dark-gray-2. Semantic tokens make theme changes and redesigns easier.

05 · Layout engineering

5. Responsive layouts that work across screen sizes

Responsive design adapts the interface to the available space and input method. Start with a usable narrow layout, then introduce additional columns or denser navigation when the content has enough room.

Common responsive patterns

  • Fluid containers: Use a maximum width and flexible side padding rather than fixed page widths.
  • Grid layouts: Use CSS Grid for two-dimensional arrangements and Flexbox for one-dimensional alignment.
  • Content-driven breakpoints: Add breakpoints where the layout stops working, not simply because a device is popular.
  • Flexible media: Ensure images do not overflow their container and preserve intrinsic proportions.
  • Touch-friendly controls: Provide adequate hit areas and spacing for mobile users.
Responsive card grid
<section class="grid grid-cols-1 gap-4 sm:grid-cols-2 lg:grid-cols-3">
  <article class="rounded-2xl border p-5">Card one</article>
  <article class="rounded-2xl border p-5">Card two</article>
  <article class="rounded-2xl border p-5">Card three</article>
</section>

Responsive image example

HTML 
<img
  src="/assets/dashboard-preview.webp"
  alt="Preview of the analytics dashboard"
  width="1200"
  height="675"
  loading="lazy"
  decoding="async"
  class="block h-auto w-full rounded-xl"
/>

Explicit image dimensions help the browser reserve space and reduce layout shifts. Use lazy loading for below-the-fold images, but generally avoid lazy-loading the primary image that is likely to be the page's largest contentful paint element.

Avoid the desktop-first trap Do not build a wide dashboard and shrink every element until it fits a phone. Rethink the information hierarchy, navigation, tables and secondary actions for narrow screens.

06 · Reusable UI

6. Component architecture and reuse

A component should represent a meaningful UI pattern with a clear responsibility. Shared buttons, form controls, cards and navigation patterns are useful abstractions; wrapping every individual HTML element in a component often adds unnecessary complexity.

Good candidates for shared components

  • Buttons with consistent variants and disabled behavior.
  • Form fields with labels, help text and error messages.
  • Cards that share layout, spacing and semantic structure.
  • Dialogs, menus and navigation patterns with reusable keyboard behavior.
  • Badges and status indicators with a controlled set of variants.

Example: a semantic button component in React

Button.jsx
const variants = {
  primary: "bg-violet-600 text-white hover:bg-violet-500",
  secondary: "border border-slate-600 text-slate-200 hover:bg-slate-800",
  danger: "bg-rose-600 text-white hover:bg-rose-500"
};

export function Button({
  variant = "primary",
  disabled = false,
  children,
  ...props
}) {
  const style = variants[variant] ?? variants.primary;

  return (
    <button
      type="button"
      disabled={disabled}
      className={[
        "inline-flex min-h-11 items-center justify-center",
        "rounded-xl px-4 py-2 font-semibold",
        "transition-colors focus-visible:outline",
        "focus-visible:outline-2 disabled:cursor-not-allowed",
        "disabled:opacity-50",
        style
      ].join(" ")}
      {...props}
    >
      {children}
    </button>
  );
}
Component design rule Prefer a small number of explicit, documented variants over arbitrary combinations of boolean props. Make the component's behavior, semantics and accessibility expectations clear.

07 · Theme management

7. Dark mode, light mode and persistent preferences

A robust theme system has three responsibilities: determine the initial theme, apply it consistently and preserve the user's explicit choice. Theme state should not cause a flash of the wrong background during page initialization.

Recommended behavior

  1. Read the saved preference before the main content renders when possible.
  2. Use a defined fallback if storage is unavailable.
  3. Apply theme values through a single class or data attribute.
  4. Use semantic color tokens so components do not duplicate theme logic.
  5. Respect the user's explicit selection rather than overriding it on every page load.

The inline script at the top of this document demonstrates early theme initialization. The toggle in the header changes the current theme and saves the preference locally. Local storage is only a convenience; it is not appropriate for storing secrets.

Minimal theme toggle logic
function applyTheme(theme) {
  document.documentElement.dataset.theme = theme;
  document.documentElement.classList.toggle(
    "dark",
    theme === "dark"
  );
  document.documentElement.style.colorScheme = theme;

  try {
    localStorage.setItem("getkit-theme", theme);
  } catch {
    // Theme still works for the current page session.
  }
}
Tailwind configuration matters This page's utility examples use Tailwind's class-based dark-mode convention. Confirm that your installed version and build configuration support the theme strategy you choose. The custom CSS variables in this document provide an independent theme mechanism.

08 · Inclusive interfaces

8. Accessibility is part of the design system

Accessibility is not a finishing touch or a color-only audit. Semantic HTML, keyboard access, meaningful labels, focus visibility, appropriate contrast and understandable feedback should be part of the original component design.

Essential checks

  • Use native buttons for actions and links for navigation.
  • Provide a visible label for every form control.
  • Keep keyboard focus visible and logical.
  • Do not communicate status through color alone.
  • Use descriptive alternative text for meaningful images; use empty alt text for purely decorative images.
  • Ensure interactive controls have practical touch targets and adequate spacing.
  • Check text and control contrast against their actual backgrounds.
  • Respect reduced-motion preferences for nonessential animation.
  • Use ARIA only where native HTML semantics are insufficient.

Accessible form example

HTML 
<form>
  <label for="email" class="block font-semibold">
    Email address
  </label>

  <input
    id="email"
    name="email"
    type="email"
    autocomplete="email"
    required
    aria-describedby="email-help"
    class="mt-2 min-h-11 w-full rounded-xl border p-3"
  />

  <p id="email-help" class="mt-2 text-sm">
    Use an address you can access.
  </p>

  <button type="submit" class="mt-4 rounded-xl px-4 py-3">
    Continue
  </button>
</form>

Do not treat a particular touch-target size or automated score as proof of full compliance. Evaluate applicable WCAG criteria, test with a keyboard and assistive technology, and review the complete interaction rather than isolated elements.

09 · Production performance

9. CSS performance, source detection and build optimization

Development convenience and production delivery are different concerns. A CDN prototype is useful for learning, but a production application should use a deliberate build process, versioned dependencies and measurable performance checks.

Recommended production workflow

  1. Pin the framework and build-tool versions in the project dependencies.
  2. Compile Tailwind using the documented workflow for that version.
  3. Make sure all template files are discoverable by the build process.
  4. Avoid dynamically generated utility names that cannot be detected.
  5. Inspect output sizes and compression in the deployed environment.
  6. Remove unused JavaScript and avoid loading large libraries for small interactions.
  7. Optimize fonts, images and third-party scripts.
  8. Measure Core Web Vitals and real user behavior after launch.

Illustrative v3 production build

Terminal — project configured for Tailwind v3 CLI
npx tailwindcss \
  -i ./src/input.css \
  -o ./dist/output.css \
  --minify

This command is specific to a CLI-based v3 setup. A v4 project or a framework using Vite or another bundler may use a different build command.

Measure the output rather than guessing

Example shell checks
# Inspect the uncompressed file size.
ls -lh ./dist/output.css

# Measure gzip-compressed output bytes.
gzip -c ./dist/output.css | wc -c

Compression results depend on the stylesheet, build tool and compression settings. Do not present a target file size as a universal performance standard. Evaluate the total page payload, caching, rendering behavior and user experience.

Core Web Vitals

Metric What it measures Common improvement areas
LCP Loading performance Optimize the main image, server response, critical assets and rendering path.
INP Interaction responsiveness Reduce long tasks, expensive event handlers and unnecessary JavaScript work.
CLS Visual stability Reserve image and ad space, avoid inserting content unexpectedly, and manage font changes.

10 · Maintainability

10. Practical architecture rules for growing projects

Keep the source organized

Separate application logic, reusable components, global tokens and page-specific composition where that separation improves clarity.

Prefer explicit variants

Use named visual variants and predictable class mappings rather than hidden conditional styling rules.

Limit arbitrary values

Use design tokens and the standard spacing scale for recurring patterns. Reserve one-off values for genuine exceptions.

Test real states

Review empty, loading, success, error, disabled, focus, hover and narrow-screen states—not just the ideal screenshot.

Suggested project structure

Example structure for a component-based frontend
src/
├── app/
│   ├── layout/
│   └── pages/
├── components/
│   ├── ui/
│   ├── navigation/
│   └── forms/
├── styles/
│   ├── input.css
│   └── tokens.css
├── features/
│   └── catalog/
└── lib/

public/
└── assets/

tests/
├── components/
└── e2e/

Adapt the structure to your framework. A small static HTML website does not need a complex component architecture or a build pipeline simply to appear professional.

11 · Quality assurance

11. Production QA: test more than appearance

A visually polished page can still fail because of broken links, missing focus styles, layout overflow, console errors or inaccessible interactions. Use repeatable checks before publishing.

Responsive testing

  • Test narrow mobile, larger mobile, tablet, laptop and wide desktop widths.
  • Check for horizontal overflow, clipped content and overlapping fixed elements.
  • Confirm that tables, navigation and code blocks remain usable on small screens.

Functional testing

  • Test every navigation link, button, form and theme control.
  • Inspect browser console and network errors.
  • Check that theme preferences behave sensibly on reload.
  • Test copy-to-clipboard behavior with appropriate fallback feedback.

Release checks

  • Verify page title, description, canonical URL and social metadata.
  • Confirm that assets return successful responses and have correct paths.
  • Check keyboard focus, text contrast and form labeling.
  • Validate performance on a production build rather than relying only on development mode.

13 · Frequently asked questions

13. FAQ: Tailwind CSS and responsive architecture

Is Tailwind CSS better than writing normal CSS?

Neither approach is universally better. Tailwind provides a consistent utility vocabulary and a productive workflow. Traditional CSS can be clearer for complex bespoke behavior or semantic styling. Many mature projects use both strategically.

Should I use Tailwind v3 or v4?

For a new project, evaluate the current stable release, framework integration and compatibility requirements. For an existing project, weigh migration cost and plugin support before upgrading. Follow the documentation for the version actually installed.

Why are some Tailwind classes missing in production?

The source scanner may not detect the class, the file may be excluded from scanning, or the production build may use a different configuration. Use complete class names, verify source paths and inspect the generated CSS.

Should every repeated element become a component?

No. Extract a component when it has meaningful repeated behavior, structure or design. Premature abstractions can make simple markup harder to understand.

Does dark mode require JavaScript?

No. CSS and the system color-scheme preference can support dark mode. JavaScript is useful when a site offers an explicit user toggle or needs to persist the user's choice across pages.

Is a small CSS bundle enough to guarantee a fast site?

No. Performance also depends on JavaScript, images, fonts, server response, layout stability, third-party scripts and interaction cost. Measure the whole page and the actual user experience.

Can I use the Tailwind CDN in production?

The browser CDN is convenient for experiments and standalone demos. For a production application, a versioned build process generally offers more predictable CSS generation, configuration and optimization.

What is the most important accessibility improvement?

Start with semantic HTML and keyboard usability. Add proper labels, visible focus, understandable error feedback and sufficient contrast, then test the complete experience against applicable accessibility criteria.
