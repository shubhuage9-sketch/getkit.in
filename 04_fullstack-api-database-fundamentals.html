01 / FOUNDATIONS

Understand the full-stack request lifecycle

A web application commonly separates the user interface, API layer, business logic, and persistence layer. This separation improves maintainability, but it also creates boundaries where authentication, validation, timeouts, and error handling must be explicit.

A serverless function may handle one request and then become idle. That does not mean the database connection problem disappears: database connections remain finite resources, and the application must use a driver and connection strategy supported by its runtime.

Reference architecture · Simplified request path 
  Browser / Mobile Client
           |
           | HTTPS request + access token
           v
  CDN / WAF / API Gateway
           |
           | TLS, routing, coarse rate limits
           v
  API Handler (Node.js / Worker / Function)
           |
           +---- Authentication & authorization
           |
           +---- Schema validation
           |
           +---- Business rules
           |
           v
  Database driver / connection pool / proxy
           |
           v
  PostgreSQL / MySQL / SQLite-compatible engine
           |
           v
  Constrained result -> API response -> Client

The exact network and pooling layers vary by host, runtime, database provider, and driver.

Define the boundaries clearly

01

Client

Displays data and collects input. It is untrusted; never rely on client-side checks to protect data.

02

API layer

Authenticates callers, validates input, authorizes actions, and returns consistent HTTP responses.

03

Business layer

Applies domain rules, transaction boundaries, ownership checks, and idempotency requirements.

04

Persistence layer

Enforces constraints and transactions, and provides indexes and query plans suited to access patterns.

Important distinction

Edge execution does not automatically make database queries faster. Latency still depends on the database's location, network round trips, query plans, connection setup, and data volume. Place compute near the data when that reduces total request latency.

02 / API DESIGN

REST vs GraphQL vs gRPC

There is no universally best API protocol. Choose based on the clients you support, how data is accessed, streaming requirements, operational complexity, and team experience.

Approach Strengths Trade-offs Good fit
REST Simple resource model, HTTP semantics, mature tooling, straightforward caching. Multiple requests may be needed for complex views; API versions require planning. Public APIs, CRUD applications, mobile backends.
GraphQL Clients select fields; nested resources can be requested through one schema. Resolver complexity, query-cost controls, authorization, and caching need care. Complex dashboards and clients with different data requirements.
gRPC Typed contracts, compact Protobuf messages, efficient RPC and streaming support. Browser interoperability and debugging may require extra tooling or a proxy. Internal services, strongly typed service-to-service communication.
WebSockets / SSE Server-pushed updates without polling every few seconds. Connection lifecycle, reconnects, fan-out, and delivery semantics add complexity. Live feeds, notifications, collaborative interfaces.

REST: use HTTP semantics intentionally

  • GET retrieves a resource and should not perform a state-changing operation.
  • POST commonly creates a resource or triggers an operation.
  • PUT replaces a resource representation; PATCH applies partial updates.
  • DELETE requests removal. Authorization and deletion semantics must be explicit.
  • Use meaningful status codes, pagination, and stable error formats.
  • Use Cache-Control and validators such as ETag when the resource's caching semantics allow it.

GraphQL: control query cost

GraphQL can reduce over-fetching, but one endpoint does not automatically mean one database query. Resolvers can produce the N+1 query problem: a list query loads many items, then performs an additional database lookup for each item. Use batching, bounded pagination, query depth or cost limits, and object-level authorization.

gRPC: optimize service contracts

gRPC uses Protocol Buffers and typically HTTP/2. It is useful for typed RPCs and streaming between compatible services. Browser-based applications may need gRPC-Web or Connect-compatible tooling; verify transport support in your chosen hosting environment.

Practical default

Start with REST for a conventional web application unless there is a clear reason to choose GraphQL, gRPC, or a streaming protocol. A simpler architecture is usually easier to secure and operate.

03 / DATA MODELING

Design a relational schema that protects data integrity

Database constraints are part of the application’s correctness model. Validate input in the API, but also use primary keys, foreign keys, unique constraints, check constraints, and transactions to protect invariants when requests race or other code paths write to the database.

Example: a digital-product catalog

This PostgreSQL example models users, products, and orders. It stores money in integer minor units to avoid floating-point rounding errors. For a multi-currency system, store the currency code as well and define how currency-specific minor units are handled.

db/schema.sql
PostgreSQL
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email TEXT NOT NULL UNIQUE,
  password_hash TEXT,
  role TEXT NOT NULL DEFAULT 'customer'
    CHECK (role IN ('customer', 'admin', 'creator')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE digital_products (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  slug TEXT NOT NULL UNIQUE,
  title TEXT NOT NULL,
  description TEXT,
  price_minor BIGINT NOT NULL CHECK (price_minor >= 0),
  currency CHAR(3) NOT NULL DEFAULT 'INR',
  asset_key TEXT NOT NULL,
  is_published BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE purchases (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id) ON DELETE SET NULL,
  product_id UUID REFERENCES digital_products(id) ON DELETE RESTRICT,
  amount_minor BIGINT NOT NULL CHECK (amount_minor >= 0),
  currency CHAR(3) NOT NULL,
  payment_provider TEXT NOT NULL,
  provider_transaction_id TEXT NOT NULL UNIQUE,
  status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'paid', 'failed', 'refunded')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_purchases_user_created
  ON purchases(user_id, created_at DESC);

CREATE INDEX idx_purchases_product
  ON purchases(product_id);

CREATE INDEX idx_products_published_created
  ON digital_products(is_published, created_at DESC);

Assumes a PostgreSQL version that provides gen_random_uuid(). Confirm version and extension requirements for your target database.

Schema design decisions

  • Unique email: prevents duplicate accounts at the database level. Normalize email consistently in the application before storing and comparing it.
  • Nullable password hash: supports accounts that authenticate through an external identity provider. Require a properly hashed password for password-based accounts.
  • Restricted product deletion: preserves purchase history. Consider soft-deleting or archiving products instead of deleting records referenced by transactions.
  • Nullable user on purchase: allows order history to survive account deletion. Choose this only if it matches your privacy and retention obligations.
  • Unique provider transaction ID: prevents the same provider transaction from being recorded twice. If the provider's identifiers are not globally unique, use a composite unique constraint including the provider.
  • Index choice: indexes should follow real query patterns. Extra indexes increase storage and write costs.
Payment integrity

Never mark a purchase as paid simply because a browser redirected to a success page. Verify payment-provider webhooks or query the provider from a trusted server, validate signatures, make event handling idempotent, and preserve an auditable record of payment state changes.

04 / DATABASE ACCESS

Use Drizzle ORM with a serverless PostgreSQL driver

An ORM can improve type safety and reduce repetitive query code. It does not replace database constraints, authorization, query-plan analysis, or transaction design.

Install the dependencies

Terminal
Shell
npm install drizzle-orm @neondatabase/serverless
npm install -D drizzle-kit typescript

Define a matching Drizzle schema

src/db/schema.ts
TypeScript
import {
  pgTable,
  uuid,
  text,
  bigint,
  boolean,
  char,
  timestamp,
  index,
  check,
} from "drizzle-orm/pg-core";
import { sql } from "drizzle-orm";

export const users = pgTable("users", {
  id: uuid("id").defaultRandom().primaryKey(),
  email: text("email").notNull().unique(),
  passwordHash: text("password_hash"),
  role: text("role").notNull().default("customer"),
  createdAt: timestamp("created_at", { withTimezone: true })
    .notNull().defaultNow(),
});

export const digitalProducts = pgTable("digital_products", {
  id: uuid("id").defaultRandom().primaryKey(),
  slug: text("slug").notNull().unique(),
  title: text("title").notNull(),
  description: text("description"),
  priceMinor: bigint("price_minor", { mode: "bigint" }).notNull(),
  currency: char("currency", { length: 3 }).notNull().default("INR"),
  assetKey: text("asset_key").notNull(),
  isPublished: boolean("is_published").notNull().default(false),
  createdAt: timestamp("created_at", { withTimezone: true })
    .notNull().defaultNow(),
}, (table) => [
  index("idx_products_published_created")
    .on(table.isPublished, table.createdAt),
  check("products_price_nonnegative", sql\`\${table.priceMinor} >= 0\`),
]);

This is a partial application schema, not a complete migration for every SQL constraint above. Keep the SQL migration and ORM schema synchronized; generate and review migrations before applying them.

Create the database client

src/db/client.ts
TypeScript
import { drizzle } from "drizzle-orm/neon-http";
import { neon } from "@neondatabase/serverless";
import * as schema from "./schema";

export function createDb(databaseUrl: string) {
  if (!databaseUrl) {
    throw new Error("DATABASE_URL is not configured");
  }

  const sql = neon(databaseUrl);

  return drizzle({
    client: sql,
    schema,
  });
}

Supply the database URL through your hosting provider's secret or environment configuration. Do not place it in browser JavaScript or commit it to source control. Confirm the exact driver and transport recommended for your database provider and runtime.

05 / API IMPLEMENTATION

Build a validated API with Hono and Zod

The following example illustrates a public product-read endpoint and a protected create endpoint. The admin middleware is deliberately an integration point: connect it to your actual authentication system before enabling writes. A CORS allowlist is not authentication and does not protect an API from direct requests.

Install API dependencies

Terminal
Shell
npm install hono zod drizzle-orm @neondatabase/serverless

Example API worker

src/index.ts
TypeScript
import { Hono } from "hono";
import { cors } from "hono/cors";
import { z } from "zod";
import { eq } from "drizzle-orm";
import { createDb } from "./db/client";
import { digitalProducts } from "./db/schema";

type Bindings = {
  DATABASE_URL: string;
};

type Variables = {
  isAdmin: boolean;
};

const app = new Hono<{ Bindings: Bindings; Variables: Variables }>();

app.use("/api/*", cors({
  origin: ["https://getkit.in"],
  allowMethods: ["GET", "POST", "OPTIONS"],
  allowHeaders: ["Content-Type", "Authorization"],
  maxAge: 86400,
}));

const createProductSchema = z.object({
  slug: z.string().min(3).max(100).regex(/^[a-z0-9-]+$/),
  title: z.string().trim().min(1).max(255),
  description: z.string().max(5000).optional(),
  priceMinor: z.number().int().safe().nonnegative(),
  currency: z.string().length(3).default("INR"),
  assetKey: z.string().min(1).max(500),
}).strict();

// Replace with real session/JWT verification and role/permission checks.
// This middleware intentionally denies writes until authentication is wired.
async function requireAdmin(
  c: Parameters[1]>[0],
  next: () => Promise
) {
  // TODO: Verify the bearer token or session with a trusted auth library.
  // TODO: Verify the authenticated identity has the product:write permission.
  // Never trust an "isAdmin" field sent by the client.
  return c.json({ error: "Admin authentication is not configured" }, 503);
}

app.get("/api/health", (c) => c.json({ status: "ok" }));

app.get("/api/products/:slug", async (c) => {
  const slug = c.req.param("slug");

  if (!/^[a-z0-9-]{1,100}$/.test(slug)) {
    return c.json({ error: "Invalid product slug" }, 400);
  }

  try {
    const db = createDb(c.env.DATABASE_URL);

    const rows = await db
      .select({
        id: digitalProducts.id,
        slug: digitalProducts.slug,
        title: digitalProducts.title,
        description: digitalProducts.description,
        priceMinor: digitalProducts.priceMinor,
        currency: digitalProducts.currency,
      })
      .from(digitalProducts)
      .where(eq(digitalProducts.slug, slug))
      .limit(1);

    if (!rows.length) {
      return c.json({ error: "Product not found" }, 404);
    }

    return c.json({ product: rows[0] }, 200);
  } catch {
    // Log a safe request ID and internal error details on the server.
    // Never return raw database exceptions or credentials to callers.
    return c.json({ error: "Service temporarily unavailable" }, 503);
  }
});

app.post("/api/products", requireAdmin, async (c) => {
  // The placeholder middleware above denies requests until real admin
  // authentication is implemented. Do not remove it to make this work.
  const parsed = createProductSchema.safeParse(await c.req.json().catch(() => null));

  if (!parsed.success) {
    return c.json({
      error: "Invalid request",
      details: parsed.error.flatten(),
    }, 400);
  }

  try {
    const db = createDb(c.env.DATABASE_URL);
    const data = parsed.data;

    const [product] = await db
      .insert(digitalProducts)
      .values({
        slug: data.slug,
        title: data.title,
        description: data.description,
        priceMinor: BigInt(data.priceMinor),
        currency: data.currency.toUpperCase(),
        assetKey: data.assetKey,
        isPublished: false,
      })
      .returning({
        id: digitalProducts.id,
        slug: digitalProducts.slug,
        title: digitalProducts.title,
      });

    return c.json({ product }, 201);
  } catch {
    return c.json({ error: "Unable to create product" }, 503);
  }
});

export default app;

Teaching example: check the Hono handler types against your installed version, and add authentication, structured logging, body-size limits, and production error handling before deployment. The create endpoint intentionally remains unavailable until real admin authorization is implemented.

Do not expose private asset locations

A product API may return public product information, but never return a private storage key or permanent download URL if that would grant access to paid files. Verify purchase entitlement on the server and issue short-lived signed download URLs where appropriate.

06 / SECURITY

Protect the API beyond input validation

Secure backend design uses multiple independent controls. Schema validation can reject malformed data, but it cannot establish who the caller is or whether that caller is allowed to access a record.

Authentication and authorization are different

  • Authentication: establishes the identity represented by a valid session or token.
  • Authorization: determines whether that identity can perform the requested action on the requested resource.
  • Ownership checks: ensure a user cannot substitute another user's ID to read or modify private data.
  • Least privilege: gives application credentials only the database and provider permissions they need.

Use parameterized queries

SQL injection occurs when untrusted data changes the structure of a SQL statement. Use bound parameters or ORM query builders for values. For dynamic column names or sort directions, use a strict allowlist because identifiers generally cannot be handled like ordinary value parameters.

Unsafe vs safe query patterns
SQL
-- UNSAFE: string concatenation changes the SQL statement.
-- Do not build a query by inserting user input into SQL text.
-- SELECT * FROM users WHERE email = '<user input>';

-- SAFE: PostgreSQL parameter binding.
SELECT id, email, role
FROM users
WHERE email = $1
LIMIT 1;

-- Example driver usage should bind the parameter separately:
-- await client.query(
--   "SELECT id, email, role FROM users WHERE email = $1 LIMIT 1",
--   [email]
-- );

Use a layered security baseline

Control Implementation guidance
Transport security Use HTTPS. Keep certificates and TLS configuration under managed hosting controls where possible.
Input validation Validate type, length, range, format, and allowed fields on the server.
Authentication Verify tokens or sessions with a trusted library; validate issuer, audience, expiry, and signature as applicable.
Authorization Check role, permission, tenant, and resource ownership on every protected operation.
Secrets Store credentials in platform secrets; rotate them and limit their privileges.
Abuse prevention Apply endpoint-specific rate limits, request-size limits, timeouts, and provider spending alerts.
Data exposure Return explicit response DTOs rather than serializing complete database rows by default.
Auditability Log security-relevant events without recording passwords, tokens, or sensitive payment data.

CORS is not access control

CORS tells browsers which origins may read certain cross-origin responses. It does not stop command-line clients, server-to-server callers, or malicious scripts outside the browser's enforcement model. Always implement server-side authentication and authorization independently.

Rate limiting: choose the right storage primitive

A counter built from separate read and write operations in a distributed key-value store can lose increments under concurrent traffic. Some edge KV products also provide eventual consistency, so they should not be treated as a strict global counter without checking their guarantees.

  • Use a managed rate-limiting service or an atomic coordination primitive for enforceable limits.
  • For per-user limits, derive the key from a verified identity rather than a client-supplied user ID.
  • For anonymous requests, account for proxy headers carefully; do not blindly trust arbitrary X-Forwarded-For values.
  • Return HTTP 429 Too Many Requests when appropriate and provide a meaningful retry policy.
  • Apply stricter limits to login, password-reset, expensive search, and write endpoints than to ordinary reads.
07 / PERFORMANCE

Connection management, indexes, and query efficiency

Serverless database connectivity

Traditional long-lived services often maintain a pool of reusable database connections. A serverless deployment may create many concurrent execution environments, and a connection per environment can exceed database limits if not managed carefully.

Pattern Advantages Watch-outs
HTTP-based database driver Fits short-lived request handlers and avoids application-managed long-lived TCP pools in supported environments. Transport limitations, round-trip cost, and transaction support vary by driver.
WebSocket driver Supports persistent session-oriented connectivity where the runtime permits it. Lifecycle management and deployment/runtime constraints matter.
Managed connection pooler Can reduce the number of direct database connections behind many application instances. Transaction pooling can change session behavior and prepared-statement compatibility.
Traditional connection pool Effective for long-lived servers with a known concurrency model. Pool size must be coordinated across every replica and background worker.
Budget connections explicitly

Estimate the total connection demand across API instances, background workers, migrations, administrative tools, and failover headroom. A pool of 20 connections across 10 replicas can represent up to 200 possible connections, not just 20.

Measure queries before adding indexes

Query investigation
SQL
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title, price_minor, currency
FROM digital_products
WHERE is_published = true
ORDER BY created_at DESC
LIMIT 20;

EXPLAIN ANALYZE executes the query and reports measured execution details. Use care with statements that modify data. A sequential scan is not automatically bad: for a small table or a query returning much of the table, it can be the correct plan.

Common performance wins

  • Return only the columns the caller needs.
  • Use bounded pagination; cursor pagination can be more stable than large offsets for frequently changing data.
  • Eliminate N+1 queries and unnecessary round trips.
  • Use caching only when invalidation and freshness requirements are understood.
  • Set query and request timeouts appropriate to the operation.
  • Batch related writes when transaction semantics permit it.
  • Monitor p50, p95, and p99 latency rather than relying on averages alone.

08 / OPERATIONS

Design for failures, not just successful requests

Return consistent errors

Clients need stable error codes and clear, safe messages. Internal logs should contain enough diagnostic context to investigate a failure, but public responses should not expose stack traces, SQL statements, connection strings, or raw provider errors.

Example error response
JSON
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Check the submitted fields.",
    "requestId": "req_example_123",
    "fields": {
      "title": ["Title is required."]
    }
  }
}

Treat the request ID above as an illustrative placeholder. Generate a unique correlation ID per request in your application or observability platform and include it in both safe logs and responses.

Retries and idempotency

  • Retry transient failures only when the operation is safe to retry or protected by idempotency.
  • Use bounded exponential backoff with jitter to avoid synchronized retry storms.
  • Do not blindly retry payment creation, email sending, or other side effects without a deduplication strategy.
  • Use idempotency keys and durable event records for workflows that may receive duplicate requests or webhooks.
  • Keep transaction boundaries short; do not hold database transactions open while waiting on slow external services.

Observability baseline

M

Metrics

Request rate, error rate, latency percentiles, database connections, query duration, and throttled requests.

L

Structured logs

Request IDs, route names, status codes, duration, and sanitized failure context.

T

Tracing

Follow a request across API handlers, database calls, and external providers where supported.

10 / QUICK ANSWERS

Frequently asked questions

Should I choose REST or GraphQL for a new project?

REST is a strong default for conventional CRUD applications and public APIs. Consider GraphQL when multiple clients need different combinations of nested data and the team can operate its schema, resolver, authorization, and query-cost controls.

Does an ORM prevent SQL injection automatically?

ORM query builders generally bind values safely when used as intended. Raw SQL fragments, dynamically constructed identifiers, unsafe interpolation, and custom query code can still introduce injection vulnerabilities. Review the generated SQL and the library's safe parameterization patterns.

Do serverless applications always need a connection pooler?

No. The correct strategy depends on the database, driver, runtime, request concurrency, and hosting provider. An HTTP-based driver may fit some serverless environments, while long-lived servers may benefit from a traditional pool or managed pooler.

Is a CORS allowlist enough to secure an API?

No. CORS is primarily a browser-enforced cross-origin policy. The server still needs authentication, authorization, input validation, and appropriate abuse controls.

Should every database column be indexed?

No. Indexes improve certain reads but consume storage and add write overhead. Use query plans and real workload measurements to decide which indexes are valuable.

How should paid digital downloads be protected?

Verify payment state using trusted server-side provider data, check the buyer's entitlement for each download request, and issue short-lived access URLs when appropriate. Do not expose private storage keys or rely only on a success-page redirect.
