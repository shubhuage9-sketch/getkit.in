01

Development Architecture & Trunk-Based Delivery

Keep changes small, test them early, and make production deployments repeatable.

Trunk-Based Development keeps the main development branch continuously usable. Developers integrate small changes frequently instead of maintaining long-lived branches that become expensive to merge. For a solo developer, a short-lived feature branch and a pull request can still provide a useful review and deployment checkpoint.

Recommended Delivery Flow

feature/... Development

Create a focused branch, edit files, run local checks, and commit a small, understandable change.

git switch -c feature/update-guide
Pull request Validation

Review the diff, run CI checks, inspect a preview deployment when configured, and resolve review feedback.

Checks must pass before merge
main Production

Merge an approved change. Your connected host builds and deploys the configured production branch.

Verify the live deployment afterward

Important: Deployment duration depends on the project, build queue, provider, and cache state. Do not promise a universal deployment time. Confirm the provider reports a successful deployment before declaring the release live.

Healthy workflow habits

  • • Keep branches focused and short-lived.
  • • Use meaningful commit messages.
  • • Review changes before merging.
  • • Test previews with realistic routes and assets.
  • • Keep a known-good production deployment available.

Patterns to avoid

  • • Force-pushing shared branches without coordination.
  • • Committing API keys or credentials.
  • • Treating a green build as proof that every page works.
  • • Caching changing HTML as immutable assets.
  • • Assuming a local hook can enforce server-side policy.
02

GitHub Branch Protection & Repository Rules

Enforce the release process on the remote repository, not just on one developer's machine.

A local Git hook can be bypassed, removed, or omitted when someone clones a repository. GitHub branch protection or repository rulesets are the correct place to enforce pull-request requirements, status checks, and restrictions on force pushes and branch deletion.

Recommended rules for main

Require a pull request before merging.

Use reviews where practical. For a solo project, a pull request can still provide a diff and CI checkpoint; review requirements depend on the repository's policy.

Require successful status checks.

Select the actual check names produced by your CI workflow after it has run at least once.

Block force pushes and branch deletion.

This reduces accidental history rewrites and deletion of the production branch.

Resolve conversations and restrict bypasses where appropriate.

Choose rules based on team size and recovery needs. Make sure trusted administrators retain an intentional recovery path.

Read GitHub's branch protection setup guide

Optional local pre-commit guard

This hook blocks a normal local commit while the checked-out branch is named main. It is only a convenience: it does not prevent direct pushes, API changes, hook removal, or bypassing Git entirely.

.git/hooks/pre-commit 
#!/bin/sh
branch="$(git symbolic-ref --quiet --short HEAD 2>/dev/null || true)"

if [ "$branch" = "main" ]; then
  echo "Blocked: create a feature branch and open a pull request."
  exit 1
fi

exit 0

Save this as .git/hooks/pre-commit and make it executable on systems that require it, for example with chmod +x .git/hooks/pre-commit. Git hooks are not normally transferred as active hooks through a clone.

Interactive Git CLI Command Reference

Everyday operations, branch management, and advanced recovery commands.

Inspect, stage, commit, and push 
git status
git diff
git add path/to/changed-file.html
git diff --staged
git commit -m "docs: improve deployment workflow guide"
git push -u origin feature/update-guide
Inspect history and remotes 
git log --oneline --graph --decorate -n 15
git remote -v
git branch -vv
git show --stat HEAD
Why not always use git add .? Stage only the files you intend to commit. Broad staging can accidentally include generated files, local configuration, or secrets. Check git diff --staged before committing.
Start a branch and sync with main 
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feature/update-guide
Stash work temporarily 
git stash push -m "work in progress"
git stash list
git switch main
git pull --ff-only origin main
git switch feature/update-guide
git stash apply

# After checking that the work was restored:
git stash drop
Clean up a branch after merging 
git switch main
git pull --ff-only origin main
git branch -d feature/update-guide
git fetch --prune

Use git stash apply when you want to inspect restored changes before deleting the stash. Use git stash pop only when you're comfortable applying and removing the stash in one operation.

Interactive rebase on a private branch 
git status
git rebase -i HEAD~4

# In the editor, use "squash" or "fixup"
# for commits you want to combine.

# If a conflict occurs:
git status
# Edit the conflicted files, then:
git add path/to/resolved-file
git rebase --continue

# To abandon the rebase:
git rebase --abort
Find the commit that introduced a bug 
git bisect start
git bisect bad
git bisect good <known-good-commit>

# Test each commit Git checks out.
git bisect good
# or:
git bisect bad

git bisect reset

Interactive rebase rewrites commit history. Avoid rebasing shared commits unless your team has agreed on the workflow.

Undo a staged file without deleting its edits 
git restore --staged path/to/file.html
git status
Discard edits to a tracked file 
# Destructive: discards unstaged edits to this file.
git diff path/to/file.html
git restore -- path/to/file.html
Recover a recent commit reference 
git reflog
# Inspect the list and identify the intended commit.
git show <commit-hash>

# Create a recovery branch before further changes:
git switch -c recovery/inspect <commit-hash>

Never run destructive reset or restore commands blindly. Inspect the working tree and preserve valuable uncommitted work first.

Automated Deployment: Cloudflare Pages & Vercel

Connect Git to the host, separate previews from production, and validate the deployed result.

Cloudflare Pages

Git-connected static deployments

  1. Open Cloudflare Dashboard → Workers & Pages → Create application → Pages → Connect to Git.
  2. Authorize the correct GitHub or GitLab repository.
  3. Choose the real production branch, usually main.
  4. Set the root directory and build configuration to match your project.
  5. Deploy, then open the generated URL and inspect the build log.

Plain HTML project
Framework preset: None; build command: blank if no build is needed; output directory: the folder containing the finished website files.

Built project
Use the actual build command and generated output directory for your framework. Do not assume /, public, or dist is correct without checking.

Official Pages setup guide

Vercel

Preview and production deployments

  1. Open Vercel Dashboard → Add New → Project.
  2. Import the intended repository and authorize access.
  3. Confirm the framework preset, root directory, and build settings.
  4. Add environment variables in the correct environment, if needed.
  5. Deploy, test the preview, and verify the production branch setting.
With Git integration, pushes to branches can generate preview deployments, while changes to the configured production branch generate production deployments. Exact behavior depends on project settings and deployment configuration.
Official Vercel Git guide

Optional GitHub Actions CI workflow

The example below runs a lightweight HTML validation check on pull requests and pushes. It does not deploy your website; Cloudflare Pages or Vercel can handle deployment separately. Review third-party action and package versions before adopting this in a production repository.

.github/workflows/html-check.yml 
name: HTML Quality Check

on:
  pull_request:
  push:
    branches:
      - main

permissions:
  contents: read

jobs:
  html-check:
    name: Validate HTML
    runs-on: ubuntu-latest

    steps:
      - name: Check out repository
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: Validate HTML files
        run: npx --yes html-validate@latest "**/*.html"

This is a starting example, not a guarantee that every existing HTML file passes validation. Pin and review dependencies for production use, configure validator rules to suit your markup, and check the action logs. If the project has no HTML files or uses a different validation tool, adapt the command.

Deployment verification sequence

01Confirm the expected commit was built.
02Inspect build logs and deployment status.
03Test navigation, assets, forms, and key routes.
04Check the live domain, HTTPS, and browser console.

HTTP Security Headers & Edge Caching

Set conservative security defaults and avoid stale content caused by incorrect cache policies.

For Cloudflare Pages, the _headers file must be included in the deployed output directory. If your build outputs to dist/, for example, the deployed file typically needs to be dist/_headers. A source file outside the published output directory may not be applied.

_headers — static site example 
/*
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  X-Frame-Options: DENY
  Permissions-Policy: camera=(), microphone=(), geolocation=()

# Long-lived caching is appropriate only for versioned or content-hashed assets.
/assets/*
  Cache-Control: public, max-age=31536000, immutable

# Revalidate HTML so visitors can receive updated pages.
/*.html
  Cache-Control: public, max-age=0, must-revalidate

/
  Cache-Control: public, max-age=0, must-revalidate

Static asset caching

Use a long max-age with immutable only when the URL changes whenever the file content changes, such as content-hashed filenames. If you overwrite assets/app.js in place, a year-long immutable cache can keep old code in users' browsers.

HTML caching

Revalidation reduces stale-page risk, but it does not guarantee every intermediary cache behaves identically. Test the actual response headers and cache behavior on the deployed domain.

Security header notes

  • Content Security Policy (CSP): Consider a carefully tested policy that matches your scripts, styles, images, fonts, and API connections. A generic strict CSP can break a site that uses CDNs or inline scripts.
  • HSTS: Enable only after confirming HTTPS works correctly across the relevant domain and subdomains. The includeSubDomains and preload options have wider consequences.
  • Permissions-Policy: Restrict browser features your site does not need, but check any embedded functionality before blocking it.
  • Provider support: Verify the target platform supports the file and syntax you're using. A static hosting header file is not automatically honored by every host.

Merge Conflicts & Production Recovery

Recover deliberately, preserve history, and verify service after the fix.

Resolve a merge conflict

Conflict markers show competing versions. Edit the file to the intended final content and remove the markers before continuing. 

<<<<<<< HEAD
<h1>Current heading</h1>
=======
<h1>Updated heading</h1>
>>>>>>> feature/update-heading
After editing the file 
git status
# Open and fix each conflicted file.
git diff
git add path/to/resolved-file.html
git diff --staged
git commit -m "fix: resolve heading merge conflict"
git push origin feature/update-heading

Revert a faulty Git commit

If a bad commit is already on the shared production branch, git revert creates a new commit that reverses the selected change. It preserves the existing history.

Git-based recovery 
git switch main
git pull --ff-only origin main
git log --oneline -n 10

# Replace <bad-commit-hash> with the actual commit.
git revert <bad-commit-hash>
git push origin main

For a merge commit, reverting requires additional care because Git needs to know which parent is the mainline. Inspect the merge and confirm the intended result before using a mainline option.

Emergency production rollback is a separate operation

If the current live deployment is broken, restoring a previously successful deployment may be faster than rebuilding a Git revert. A hosting-platform rollback changes what is serving traffic; a Git revert changes repository history and normally triggers a new deployment when pushed.

Vercel

Use the project's deployment controls to roll back to a known-good deployment. The CLI also provides rollback functionality for linked projects.

vercel rollback
vercel rollback status
Vercel rollback guide

Cloudflare Pages

Open the Pages project and inspect its deployment history. Follow the current platform controls for restoring a prior version or redeploying a known-good commit. Available options depend on the project's deployment method.

Cloudflare Pages documentation

After recovery, verify the production URL, key routes, browser console, assets, and service behavior. Then identify the cause and prepare a reviewed permanent fix. A rollback can restore application code but may not reverse database changes, external side effects, or incompatible data migrations.
